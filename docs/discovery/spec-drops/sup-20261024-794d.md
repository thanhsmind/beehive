## What design-os is (from the originating session)

Repo `/mnt/data/Projects/goglbe/design-os` (main @ a7ad5f1), npm package
`ease-design@0.6.1`, binary `ui`. It has three parts:

1. **`knowledge/`** — about 60 Markdown files of design taste (color,
   typography, spacing, a11y, charts, motion, SwiftUI, and more). An agent
   reads them selectively.
2. **The `ui` binary** — a deterministic CLI (no LLM, no network):
   linters (`a11y-lint`, `taste-lint`, `validate-layout`, `content-lint`,
   `ds-usage-lint`, `token-coverage`), `autofix`, and
   `ui gate <page.html> --dir .`, which merges every linter into one
   PASS/FAIL verdict. It also compiles tokens and onboards a design system
   from CSS or Figma (`ingest-css-ds`, `ingest-figma-ds`, `ds import`).
3. **The adapter** — `ui init --runtime claude|codex|antigravity` writes
   `.claude/commands/ui/*.md` (20 `/ui:*` commands) and
   `.claude/skills/design-os-*/` into a project. For Codex it upserts a
   sentinel block in AGENTS.md.

## Field evidence (for triage, not decisions)

design-os is being adopted into anphabe-goglbe (a project that uses bee)
through run `run-6d9a362bfd2e37d7`, worktree `wt/design-os-adopt`:

- Baseline `ui gate`: 882 errors / 323 warnings over 20 pages.
- Plan: 6 cells — a11y fixes, onboard the design system from
  `anphabe-ui.css`, `ui init`, and a CI ratchet in `.gitlab-ci.yml`.
- Finding: 15/15 `unclosed-structural-tag` hits are linter false positives
  (a CSS comment that contains `<header>`).
- Finding: `tiny-body-text` (body ≥16px) is a landing-page rubric. It is
  noise on data-dense dashboards.

## Possible integration directions (no decision taken)

- **A. Optional install at `bee onboard`.** When a project has a UI
  (HTML/CSS/React…), `bee onboard` offers to run `ui init` and onboard the
  design system.
- **B. `ui gate` as proof for UI cells.** A cell that touches UI files must
  carry `ui gate` output that is PASS (or not above baseline), as a bee
  proof rule.
- **C. Reference only.** Add a craft guide or expertise entry that points
  to design-os, with no packaging.

Open questions:

- An npm dependency (`ease-design`) versus a self-contained bee-rs.
- Skill overlap: bee skills and design-os skills in the same
  `.claude/skills`.
- License: design-os is PolyForm Shield 1.0.0. Check whether it is
  compatible with how bee is distributed.

## Feasibility check, 2026-10-24 (evidence for triage, not decisions)

- **B works today with no bee change.** A host can put `ui gate` in its
  declared `commands.test`; bee caps record that command as the proof line
  and CI runs it. A hard PASS is not usable yet: the field run shows linter
  false positives and a landing-page rubric on dashboards, so a baseline
  ratchet is the honest form.
- **A has a precedent.** `bee onboard` already makes an offer-only step
  (`NO_TEST_VERIFICATION_OFFER`, see
  `docs/knowledge/areas/onboarding/host-project-artifacts.md`). A design-os
  offer could follow it: detect a UI, offer `ui init`, never install.
  This needs a bee-rs change.
- **No skill clash.** Onboarding removes only `bee-*` skills
  (`packages/bee-rs/crates/bee/src/onboard/skills.rs:882`). design-os writes
  `design-os-*` skills and `/ui:*` commands.
- **C fits a guide, not `expertise/`.** `expertise/frontend.md` is
  tool-free by design, so a pointer to a tool belongs in a craft guide or a
  knowledge concept.
- **Bundling is the risky path.** bee-rs is a self-contained Rust binary;
  bundling adds a Node runtime. PolyForm Shield 1.0.0 allows distribution
  with the notice, but its Noncompete clause needs a human call. This repo
  has no LICENSE file, so bee's own distribution terms are not set.

- **`ui init` installs everything.** In anphabe-goglbe it wrote 23
  `design-os-*` skills and 23 `/ui:*` commands, including native iOS,
  iPadOS and macOS, shader, scroll-cinema, gflow and Figma kits that a web
  dashboard never uses. `ui init` has no subset flag. Direction A would
  carry that whole tree into every host unless bee picks a subset.

## Owner input, 2026-10-24 (input for triage, not a locked decision)

The owner wants install to work like akkit: at install time, the user picks
which skills fit this project type, and unneeded skills are never written.

Notes for triage:

- `bee onboard` has no skill-selection flag today; it installs bee's own
  skills only.
- The skill-to-project-type map belongs to design-os, which owns its skills.
  `ui scan` already detects a project's framework and styling, so a
  `ui init` profile or picker could use it. bee would only pass the choice
  through, not keep a second copy of the map.

Later the same day the owner went further: bring design-os *into* bee, so
that bee's design agent carries this taste, instead of keeping design-os
separate.

Notes for triage:

- bee has no visual/UI design role today (`bee team show`). `lane-1..3`
  are blind seats for *software* design proposals; `hat-user-impact` (the
  SEE mock) is the closest to UI. The team role set is open, so a UI
  design role is a config addition, not a new mechanism.
- Vendoring design-os code or `knowledge/` into bee is distribution under
  PolyForm Shield 1.0.0 (licensor: Jang Trinh). It needs the notice, and
  its Noncompete clause needs the licensor's view or a human legal call
  before anything ships.
