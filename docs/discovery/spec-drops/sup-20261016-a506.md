# Check with evidence what piggery could improve in bee (the beehive part)

Provenance: from waggledance@e8b3751, correlation id sup-20261016-a506, 2026-10-16.

## The ask, as received (condensed from Vietnamese)

piggery (https://github.com/sting8k/piggery, read-only local copy at
`/mnt/data/Projects/refs/slp/piggery`, v0.10.2) is a Go + SQLite + unix-socket
daemon. It is a shared mailbox for every agent on the machine (a mail is acked
only when the turn that handles it ends normally), and a code-enforced gate over
every mail and every spawn from a YAML manifest (who may mail whom, who may
spawn whom, concurrency, depth, rate). It also spawns and manages headless
workers, runs workers in a git worktree (`can_set_cwd`), and fires a notify hook
when a mail flow needs a human.

The owner said no multi-harness support is needed, because bee is already the
harness. Only Claude Code and Paseo, as bee runs them today, are in scope.

Six hypotheses, each judged against this repo's own code and docs as: right and
worth doing / bee already has an equivalent / not worth it / wrong premise:

1. piggery as the runtime for bee-swarming workers.
2. A more durable mail model than `.bee/mailbox`.
3. Code-enforced limits (parallel workers, depth, rate).
4. Worktree per cell (`can_set_cwd` + `spawn.allowed_roots`) versus bee's
   feature worktrees and `paseo-worktree-workspace`.
5. `dual-lens` / `council` taskforce templates versus `bee-reviewing`.
6. Worker lifecycle (abort, tree kill after 2 s, resume, wake on death) versus
   `bee herding` and the control loop.

bee's "gate" (a human approval in `.bee/state.json`) and piggery's "gate" (a
routing door and a team's representative session) are different concepts.

Risks to name: two parallel mail systems; piggery is single-machine; a third
daemon beside waggledance and Paseo.

Scope: assessment only. No product code change, no piggery integration. One
`proposed` PBI per worthwhile item.
