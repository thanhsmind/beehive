## Context gathered in the originating session (for triage, not decisions)

- A pstack playbook is a plain markdown file, not a skill. It names a task
  type and holds ordered steps, gates, the skills each step calls, and a
  per-task reply contract. The mode skill matches the request to one
  playbook. It copies the steps verbatim into the todo list, and a step can
  only be dropped with a written `skip: <reason>`.
- Bee's `expertise/` is a different layer. It holds craft and domain
  *judgment* ("what good looks like", routing tables). It is deliberately
  universal-software and tool-free, and it never references skills or
  workflow. A playbook is *procedure* ("which steps, which gates, which
  output, for this task type"), and it calls skills and cites expertise. So
  playbooks would likely complement expertise rather than replace it.
- Most of the value of a pstack playbook is in its gates against model
  shortcuts (repro yourself, "inconclusive is not a pass", verify on the
  real artifact), plus team-specific context and the output contract. Its
  step-by-step how-to matters much less.
- The human's stated extension is into non-software domains: marketing,
  content, sales. Bee's pipeline (worktrees, verify command, tests) assumes
  code. A non-software playbook would need its own notion of verification.
  One example would be a brand-review or claims check as the gate. The human
  already has Anphabe content skills (anphabe-content,
  anphabe-card-to-content, marketing:brand-review) that such playbooks could
  call.
- Open questions for triage: whether playbooks sit alongside `expertise/` or
  inside bee-hive routing; whether software playbooks would overlap bee's
  existing shaping → planning → swarming chain; and how a non-code playbook
  proves "done".
