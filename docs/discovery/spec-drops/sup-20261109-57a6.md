## Owner decisions (settled in the originating conversation)

1. Flow, not gate. No new gate and no mandatory knowledge-ref check.
   Loading and writing knowledge are ordinary steps of the flow.
2. Read: at shaping (context lock) and planning, bee assembles one feature
   pack = knowledge context (areas, patterns, past decisions) + the code
   files those concepts anchor (`bee.anchors`). The shaping interview,
   CONTEXT.md, the load-bearing claims in plan.md and the hat-wave briefs
   all use the same pack. Code and knowledge complement each other;
   neither repeats the other.
3. One assembler: reuse `learned_context_lines`, so shaping, planning and
   cells read the same pack.
4. Write proactively: each cell writes its knowledge delta (area update, a
   pattern when it hit a pitfall, anchors to the files it changed) in the
   same commit as its code at cap. Knowledge never trails code.
5. Close and merge only consolidate: a writer-role worker dedupes and
   writes the delivery, and the knowledge lands in main in the same merge
   as the code. The `promote-proposals.md` backlog goes away.
6. No human review step, critical patterns included. Fix it later, like
   code.
7. Keep the layer thin: every entry anchors to code and never restates
   what code shows. The close-time writer trims repetition.
8. Keep measurement: record the loaded pack paths in `dispatch.jsonl`.
   Keep the 10% hash holdout (D4 of knowledge-outcome-measure) at feature
   level as well as at cell level.
9. Drain the existing debt once (proposals, capture stubs, orphaned
   scribing) through the same flow.

## Wanted outcome (for this repo's chain to shape and plan)

A feature run end to end shows:

1. The pack is loaded at shaping and at planning.
2. Each capped cell commit carries its `docs/knowledge/` delta.
3. The merge to main contains code and knowledge together.
4. No new `promote-proposals.md` is left unapplied.
5. `bee knowledge report` shows recorded arms.
