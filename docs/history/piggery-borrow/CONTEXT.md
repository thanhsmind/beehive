## Feature Boundary

A study of the piggery reference repo (`/home/thanhsmind/Projects/refs/piggery`,
v0.6.0, two advisor digests on 2026-10-06) found seven practices bee should
adopt or adapt. They were filed as backlog items p-596857ac, p-7fd7ef0e,
p-a0609bac, p-91e36c63, p-215ba2a9, p-5771b088 and p-cf8f7437. This feature
delivers all seven. The skipped ideas (a shared tools.json, peer mail routing
and rate limits, pi MCP for the belt, a TUI, YAML team templates) stay out.

## Locked Decisions

| ID | Decision | Rationale (only if it changes implementation) |
|----|----------|-----------------------------------------------|
| D1 | The pi belt records the `outcome` that `agent_before_settle` reports for the active leader turn (pi 0.87.0 and newer send `completed`, `aborted` or `error`), before any early return in that handler. At `agent_settled`: on `completed` it deletes the in-flight result-inbox claims; on `aborted` or `error` it requeues each claim with `requeueClaim` and HOLDS the requeued claims, so the drain does not inject them until the next turn the user starts (the next `input` event); when no outcome was seen (pi older than 0.87.0) it keeps today's delete. The drain skips its tick while a UI prompt is open for the session (`promptDepths` above 0). Revised after the hat wave. (p-596857ac) | piggery acks mail only on a turn that ended ok and a failed or aborted turn does not wake itself (`internal/core/harness.go:269-313`). Without the hold, Esc would restart the leader 2 seconds later, and an error turn would loop. |
| D2 | `bee herding cancel` stops the worker's whole process tree on unix. Before it closes the pane, it reads the tree below the captured foreground pid with one `ps -A -o pid=,ppid=,pgid=` call, sends SIGTERM to the tree, waits up to 2 seconds, re-reads, and sends SIGKILL to every member still alive; then it closes the pane and confirms exit as today. The tree reader and the signal sender sit behind seams so tests never signal the test runner. The 5-second fail-closed rule and `cancel_termination_failed` stay. Windows keeps today's behavior, and Paseo workers keep `paseo stop`; the cancel help says both. Revised after the hat wave. (p-7fd7ef0e) | piggery reads the tree first because orphans reparent to init and cannot be found later (`internal/driver/local/proctree.go:10-14`). A pane close today relies on SIGHUP and detached children survive. |
| D3 | `.bee/config.json` may set `herding.limits.concurrency` (live herding workers) and `herding.limits.depth` (nested `bee herding run` levels); absent means no limit. Both doors count occupancy through one new read-only helper that prints nothing and writes nothing: the wave ledger's live worker count over a quiet pane list, with Paseo agents counted as live even when no pane list is available. `bee herding run` refuses before spawn with `{ok:false, reason:"limits.concurrency", live, limit, retryable:true, fix:"wait for a worker to finish (bee herding status) or raise herding.limits.concurrency"}`, with `limits.unverifiable` when only a fallback count exists and a concurrency limit is set, and with `limits.depth` when its depth (`BEE_HERDING_DEPTH`, absent = 0) reaches the limit. `BEE_HERDING_DEPTH` (own depth plus one) is exported to the child only when a depth limit is set, so a config with no limits gives byte-identical output. `bee dispatch prepare` runs the same checks when the role resolves to a herding agent (`Resolved::Herding`). `bee dispatch prepare --explain` prints each check (role, claim, limits) with pass or refuse, in plain text or with `--json`, and stops before any claim, reservation or record write. The cockpit spawn path (`herdr agent start` plus `record-worker`) is outside these two doors. Per-role `can_dispatch` is split out to backlog. Revised after the hat wave. (p-a0609bac) | The four-slot cap lives only in a markdown role today; piggery refuses at the spawn door with a rule id (`internal/core/agent.go:93-110`). The existing occupancy verb prints and marks orphans, so it cannot run inside prepare. |
| D4 | The pi and opencode belts declare `BELT_CONTRACT_VERSION` and send it inside the session-init stdin payload as `belt_contract: {belt, version}`, so the hook helpers keep their argv. The binary holds its own contract number. On a mismatch, session-init returns one line naming the side to update (belt older: `bee onboard --apply`; binary older: the binary-freshness remedy), and the belt shows that line to the human (`ctx.ui.notify` on pi, a toast on opencode) as well as in the preamble. A payload with no `belt_contract` is accepted as contract unknown. The doctor row for the belt contract belongs to D7's runtime rows. Bump rule: any change to a `bee hook` stdin shape or a belt-visible verdict shape bumps both. Revised after the hat wave. (p-91e36c63) | piggery's PROTOCOL_VERSION handshake tells the user which side to update (`extensions/pi/index.ts:134-142`). The preamble alone reaches the model, not the human. |
| D5 | The pi belt keeps its session state on one `globalThis[Symbol.for("bee.pi.state")]` slot created with `??=`, fills any missing default field on a kept slot, and moves the module-level maps (`inFlightClaims`, `promptDepths`, `forcedContinuationSessions`, and D1's outcome record) onto it, so a `/reload` with a fresh module scope keeps them and session-init runs once. The leader decision is taken once per process. Only when the process is the Paseo leader does the belt keep `PASEO_AGENT_ID` in the slot and remove it from `process.env`; workers keep it, so the worker Bash guard and the hidden leader tools are unchanged. Every belt reader of the id (events.ts, index.ts, paseo-heartbeat.ts) reads the slot, and every belt spawn of `bee` or `paseo` (bee-cli.ts, hooks.ts, tool-dispatch.ts, paseo-heartbeat.ts) passes the id back. A `bee` command the leader's model runs from its own shell no longer sees the id; that is accepted, because a job's Paseo agent is never the leader. `BEE_HERDING_WORKER` and `BEE_HERDING_JOB_ID` are never stripped. Revised after the hat wave. (p-215ba2a9) | piggery keeps per-process state on globalThis and strips its identity from children (`extensions/pi/index.ts:34-63`). |
| D6 | The activity hook records the worker's `transcript_path` (which it already receives) in the job's mailbox activity record. `bee herding status` reads that transcript with the usage parser `bee dev statusline` already has and adds `ctx_tokens` (the input plus cache tokens of the latest assistant request, the context size the worker is at now) and `turns` (assistant messages) per job to its JSON, and a `ctx=12.3k turns=4` suffix to the plain line. When no transcript path is recorded (pi child workers run with `--no-session`, Paseo pi workers share one agent folder) or the file is unreadable, both fields are `null` and the suffix is omitted. The pi `bee-workers` widget is not changed: it reads only result markers, so the widget suffix is split out to backlog. Revised after the hat wave. (p-5771b088) | `piggery top` shows a worker's context and turns read from its transcript (`view/text.go:44-52`). The worker log.txt is free text and carries no token data. |
| D7 | `bee doctor` adds one advisory row per runtime bee supports (claude, codex, opencode, pi, paseo) in the advisory channel, so the verdict never changes because of them. Each row names whether the tool is found on PATH (located, never executed, so a wrapper script never runs), whether the repo's bee wiring for that runtime is present and current, and on every not-ok row a `fix:` line: the exact bee command for stale or missing wiring (`bee onboard --apply`), or an install line naming the missing tool when only the tool is missing. The pi and opencode rows also carry the belt contract check from D4 (the belt source's `BELT_CONTRACT_VERSION` against the binary's), with one fix. Revised after the hat wave. (p-cf8f7437) | `piggery setup` prints one line per harness with its fix command (`internal/cli/setup.go:178-218`). Doctor's verdict blocks on any mechanical row that is not ok, so the new rows must be advisory. |
