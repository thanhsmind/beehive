# Verification: foundations

How to run this file: `bee` in every Steps cell means the pinned binary — beehive's `.bee/bin/bee` at commit `6b0ae488`, called by absolute path or put on `PATH` for the pass. Most rows run in a **scratch** host repo: `mkdir -p host/.bee && echo '{}' > host/.bee/onboarding.json`, then run everything from inside `host/`; delete the directory between documents so no queue, lane, or session record leaks from one section into the next. No hooks fire in a scratch repo, which is exactly why the binary's own answers can be read there without a guard in the way. Rows marked **hooked** need a live Claude Code session with bee's hooks wired, in a disposable clone of a host repo — nothing else shows a deny, a repair, the preamble, or an injected nudge. **worktree** needs `bee worktree new` run once plus the main checkout; **two sessions** needs two live hooked sessions in one checkout; **piped** means stdout or stderr redirected (`>/dev/null`, `2>/dev/null`) for a stream-split check; **codex** rows stay `blocked` until a Codex runtime is available. Check exit codes with `; echo $?` after every command whose Expected names one. Never hand-edit a store file in a hooked checkout to set up a row — the deny is the point of the guard; use the scratch repo when a row needs a store file shaped by hand, and say so in the note.
