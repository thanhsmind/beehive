# Verification: lifecycle

How to run this file: work in a **scratch host repo**, never in beehive itself — `mkdir -p host/.bee && printf '{}' > host/.bee/onboarding.json && git -C host init -q && git -C host config user.email t@example.com && git -C host config user.name tester` — and run every command from inside `host/`, with `bee` meaning the pinned `.bee/bin/bee` from the beehive checkout (absolute path). No hooks fire in the scratch repo, so the binary's own behavior is isolated; delete `host/` and rebuild it between documents, and rebuild it again after any row that leaves a lane blocked.

Most rows need **fixture L** — one lane record with Gate 2 open — built in four commands from a fresh `host/`:

```
export CLAUDE_CODE_SESSION_ID=s1
bee state start-feature --feature demo --mode standard --as-lane --session-id s1
bee state session bind --session-id s1 --lane demo
bee state plan-conflicts derive --lane demo         # a fresh repo derives zero candidates: an empty, complete review
bee state gate --merge --approved true --lane demo  # Gate 2 open for lane "demo"
```

Variants named in the Setup column:

- **fixture L-ungated** — the first three commands only; Gate 2 stays unapproved.
- **fixture L-bare** — the first two commands only; no conflict review derived.
- **fixture L+cell** — fixture L, then one cell:
  ```
  bee cells add --stdin <<'JSON'
  {"id":"demo-1","feature":"demo","title":"Add a note","action":"Append one line to notes.txt","verify":"true","lane":"small","role":"code","files":["notes.txt"],"affects_skills":[],"affects_specs":[]}
  JSON
  ```
- **fixture L+claim** — fixture L+cell, then `bee cells claim --id demo-1 --worker w1 --session-id s1`.
- **fixture L+cap** — fixture L+claim, then a commit carrying the trailer and a green cap:
  ```
  printf 'note\n' > notes.txt && git add notes.txt
  git commit -q -m "Add a note" -m "cell: demo-1"
  bee state worker add --nickname w1 --cell demo-1 --status running
  bee cells finish --id demo-1 --files notes.txt --report '{"outcome":"note added","commit":"HEAD","files":["notes.txt"],"tests":"true — green — touched notes.txt only","deviations":[]}'
  ```

`bee state route` takes **no** lane-targeting flag, so route rows depend on the session binding from fixture L; `gate`, `plan-conflicts`, `plan-rev`, and `scribing-run` accept `--lane demo` directly. Needs values follow [the README](README.md#needs-and-conditions): `scratch`, `hooked`, `worktree`, `two sessions`, `piped`, `codex`. A **two sessions** row runs a second terminal in the same `host/` with `CLAUDE_CODE_SESSION_ID=s2`. Check every exit code with `echo $?` and every stream split with `2>/dev/null` and `>/dev/null`; read the store back with `cat .bee/lanes/demo.json`, `cat .bee/cells/demo-1.json`, `ls .bee/claims/` — observing the store by hand is fine, writing it by hand is what the guards deny.
